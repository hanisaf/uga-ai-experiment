AI-Assisted Passenger Screening · AI 보조 출입국 심사

Design overview and test URLs for the behavioral screening task. Participants review 15 fictional passenger case files alongside a simulated AI risk score under a countdown timer, and decide Allow / Secondary — Rejection / Secondary — Info for each. Behavioral data is exported back to Qualtrics via URL parameters.

Behavioral task · 15 scenarios   |   Safadi · Kim · Schanke — UGA / UCF · August 2026

▸ Launch the task 과제 실행

The instrument is the single file survey.html. It loads assets/scenarios.json and the images in assets/ at runtime, so it must be served over HTTP — opening it as a file:// path will hang on "Loading case files…". Every link on this page is relative, so it works on any host.

Serving locally

From inside the design_handoff_screening_terminal/ folder:

python3 -m http.server 8731
# then open  http://localhost:8731/

Any static server works (npx serve, php -S, nginx, S3…). The only requirement is that index.html, survey.html, and assets/ are served from the same origin.

Production hosting

Upload survey.html, this index.html, and the entire assets/ folder (same relative paths) to any static host. The participant-facing URL is then https://YOUR-HOST/path/survey.html?….

▸ URL parameters URL 매개변수

All parameters are read from the query string (?key=value&key=value).

ParamValuesDefaultRole in the study
transparent 1 / 0 1 Between-subjects IV. 1 shows the AI's bilingual "Contributing factors" list; 0 hides it (score + recommendation only). This is the condition you randomize.
queue_size 50 / 200 / 500 200 Between-subjects condition. Passengers waiting, shown as a chip beside the timer and held constant for the whole session. 50 = light traffic, 200 = normal load, 500 = very busy. Any other value falls back to 200. Randomize this in Qualtrics alongside the transparency condition.
order random / default / id list per-session shuffle Presentation order. Omit for the production design (fresh constrained shuffle per participant). random = the same constrained shuffle for everyone, from order_seed; default = authored order; a comma-separated id list forces that exact sequence (omitted ids are appended, never dropped).
order_seed int 42 Seed for order=random. Ignored in every other mode.
guid string auto UUID Session ID written into the exported data. Pass the Qualtrics ResponseID here so behavioral records join back to the survey response.
return_url URL none Qualtrics survey URL to redirect back to on completion; the export query string is appended. Required to collect data back.
auto_return 1 / 0 on in prod Auto-redirect to return_url when the session ends, so data isn't lost if the participant closes the tab. On whenever return_url is set; off in debug.
return_delay int 0–60 6 Seconds the results screen shows before auto-return. 0 = redirect immediately.
debug 1 / 0 0 QA only — shows each scenario's difficulty rating inline and disables auto-return so you can inspect the export screen. Never enable in production.
Careful with transparent. The default 1 applies only when the parameter is absent. Any other present value (e.g. 2, yes, empty) is treated as 0 (opaque) — so always pass exactly 1 or 0.
The timer counts up, not down. Each passenger opens at 0:00 · 경과 시간 and accumulates while the officer deliberates. There is no ceiling, no expiry and no forced decision — Incheon officers have no hard per-passenger limit, only an internalised norm of about 60 seconds, so a countdown would imply a deadline that does not exist. Accumulating time supplies the queue pressure instead, and the elapsed value itself (sN_time) is the behavioural measure. The norm is shown beside the timer as 팀 평균 ~60초. (This supersedes the August 2026 countdown and its OVERTIME flag; timer_sec and sN_expired no longer exist.)
Officers cannot deny entry. Denial is an administrative decision taken above the frontline after secondary review, so the interface offers Allow Entry, Secondary — Recommending Rejection, and Secondary — Requesting Additional Information. Either secondary option reveals an optional free-text box (300 characters) for the basis of the referral. The old Deny Entry button is gone, and sN_dec is now coded a / sr / si / NA.
Leave order unset in production. Omitting it gives each participant a fresh shuffle with the AI-error trials (S5, S9) kept out of the first two and last two positions. order=random is the opposite — one fixed sequence for everyone — so use it for pilots and demos, not for a live wave where you want order counterbalanced across participants.

The app always exports the values it actually used, so the condition each participant ran is recoverable from the returned data alone. The sequence actually presented always comes back as scenario_order, whichever mode produced it. A queue_size outside {50, 200, 500} falls back to 200, and an unrecognised order value falls back to the default per-session shuffle.

▸ Randomizing across participants 참가자별 무작위 배정

The manipulated factor is transparency (2 cells). Queue load is a between-subjects condition that can be treated as a third factor or as a covariate. Pick one of the two designs below.

Approach A — Recommended

Randomize transparent and queue_size independently per participant. Transparency is the manipulated factor; queue load enters analysis as a covariate first and as a moderator in follow-up, which is the recommendation while cell sizes are uncertain.

# Transparent (AI explanation shown)
survey.html?transparent=1&queue_size=<50|200|500>&guid=<RESPONSE_ID>&return_url=<QUALTRICS_RETURN>

# Opaque (score only, no explanation)
survey.html?transparent=0&queue_size=<50|200|500>&guid=<RESPONSE_ID>&return_url=<QUALTRICS_RETURN>

Approach B — Full factorial

Treat queue load as a third factor: cross queue_size ∈ {50, 200, 500} with transparent ∈ {0, 1} → 6 cells. With ~1,000 officers that is ~166 per cell, which is workable but leaves less headroom than the 2-cell design; the team's standing recommendation is to analyse queue load as a covariate first and only treat it as a factor if the effect warrants it.

▸ Wiring it up in Qualtrics Qualtrics 연동

Don't hand out static per-participant URLs. Qualtrics assigns the condition and builds the URL for each respondent on the fly, piping its own ResponseID in as the guid.

  1. Randomize the condition. Add an Embedded Data field transparent, then use a Randomizer that sets transparent=1 on one path and transparent=0 on the other (Evenly Present = balanced). Add a second Embedded Data field queue_size with its own randomizer over 50/200/500 (or 6 combined paths for Approach B).
  2. Place the task on a survey page as a full-width iframe or a redirect, with parameters piped from embedded data:
survey.html?transparent=${e://Field/transparent}&queue_size=${e://Field/queue_size}&guid=${e://Field/ResponseID}&return_url=${e://Field/return_url}
  1. Set return_url to the survey's own continue URL. When the participant finishes, the task auto-returns them there with all behavioral data appended (no click needed).
  2. Capture the returned data by declaring matching embedded-data fields on the return page (see next section).
Keep guid = ResponseID. That single key is what lets you join the rich behavioral export to each Qualtrics response afterward.

▸ Collecting the data back 데이터 수집

When the participant finishes the 15th decision, the app builds one query string of all results and redirects the browser to return_url with it appended. Two safeguards make this reliable in the field:

  • Auto-return fires on its own (default 6 s, tunable with return_delay) so data still returns if the participant walks away — a "Submitting your data…" banner and a manual button back it up. Off in debug.
  • URL-length guard. Referral comments are the volatile part: Korean percent-encodes to about nine characters each, so fifteen filled comments can exceed the 7500-char cap on their own. The app sheds the bulky events_log first, then the comments, setting events_log_dropped=1 and comments_dropped=1 so the loss is visible in the data. All summary fields always survive, and the complete record stays recoverable via Copy export data.

To record the data, point return_url at a Qualtrics survey and add an Embedded Data element at the top of its Survey Flow listing every field name below (no values) — Qualtrics auto-fills each from the matching URL parameter. Because guid = ResponseID, join on guid to attach it to the participant's response.

The Embedded Data field list changed shape — not just size. Six families were removed (timer_sec, sN_expired, n_expired, sN_correct, sN_difficulty, sN_override) and new ones added (queue_size, sN_comment, fp2_caught), while n_correct was renamed correct_total. Delete the retired fields and add the new ones before your next wave, or you will collect empty columns alongside stale ones.

Single-response alternative. If you need the task data on the same Qualtrics row rather than a joined one, embed survey.html in an iframe inside a question and post the results to the parent with window.postMessage, then write them to embedded data with question JavaScript. That's more setup than the join-by-guid flow above, and only worth it if a second linked record is a problem for you.
