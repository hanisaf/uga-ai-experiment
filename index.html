AI-Assisted Passenger Screening · AI 보조 출입국 심사

Design overview and test URLs for the behavioral screening task. Participants review 15 fictional passenger case files alongside a simulated AI recommendation, with elapsed time counting up, and decide Allow Entry / Secondary — Checking / Requesting Further Information / Secondary — Recommending Rejection for each. Behavioral data is exported back to Qualtrics via URL parameters.

Behavioral task · 15 scenarios   |   Safadi · Kim · Schanke — UGA / UCF · August 2026

▸ Launch the task 과제 실행

The instrument is the single file survey.html. It loads assets/scenarios.json and the images in assets/ at runtime, so it must be served over HTTP — opening it as a file:// path will hang on "Loading case files…". Every link on this page is relative, so it works on any host.

Serving locally

From the project folder:

python3 -m http.server 8731
# then open  http://localhost:8731/

Any static server works (npx serve, php -S, nginx, S3…). The only requirement is that index.html, survey.html, and assets/ are served from the same origin.

Production hosting

Upload survey.html, this index.html, and the entire assets/ folder (same relative paths) to any static host. The participant-facing URL is then https://YOUR-HOST/path/survey.html?….

▸ URL parameters URL 매개변수

All parameters are read from the query string (?key=value&key=value).

ParamValuesDefaultRole in the study
transparent 1 / 0 1 Between-subjects IV. 1 shows the AI's bilingual "Contributing factors" list; 0 hides it (recommended decision + confidence only). This is the condition you randomize.
show_confidence 1 / 0 1 Between-subjects condition. 1 shows "System confidence in this recommendation · NN%" beneath the AI's recommended decision; 0 hides it, leaving the recommendation with no numeric cue at all. Independent of transparent, so the two can be crossed or either held constant. The value used is exported as show_confidence.
queue_size 50 / 200 / 500 200 Between-subjects condition. Workload, held constant for the whole session and shown beside the timer as a day-type label, not a headcount — 50 = "Light traffic · 한산한 날", 200 = "Normal load · 보통 날", 500 = "Busy day · 바쁜 날". The raw integer is still what gets exported. Any other value falls back to 200. Randomize this in Qualtrics alongside the transparency condition.
order random / default / id list per-session shuffle Presentation order. Omit for the production design (fresh constrained shuffle per participant). random = the same constrained shuffle for everyone, from order_seed; default = authored order; a comma-separated id list forces that exact sequence (omitted ids are appended, never dropped).
order_seed int 42 Seed for order=random. Ignored in every other mode.
guid string auto UUID Session ID written into the exported data. Pass the Qualtrics ResponseID here so behavioral records join back to the survey response.
return_url URL none Qualtrics survey URL to redirect back to on completion; the export query string is appended. Required to collect data back. Also accepted spelled returnUrl; return_url wins if both are present. Prefer the snake_case form — the alias exists only for backward compatibility.
auto_return 1 / 0 on in prod Auto-redirect to return_url when the session ends, so data isn't lost if the participant closes the tab. On whenever return_url is set; off in debug.
return_delay int 0–60 6 Seconds the results screen shows before auto-return. 0 = redirect immediately.
debug 1 / 0 0 QA only — shows each scenario's difficulty rating inline, adds a ⚡ Skip button that auto-selects Allow and advances (so you can walk all 15 quickly), and disables auto-return so you can inspect the export screen. Never enable in production.
Careful with transparent. The default 1 applies only when the parameter is absent. Any other present value (e.g. 2, yes, empty) is treated as 0 (opaque) — so always pass exactly 1 or 0.
The timer counts up, not down. Each passenger opens at 0:00 · 경과 시간 and accumulates while the officer deliberates. There is no ceiling, no expiry and no forced decision — Incheon officers have no hard per-passenger limit, only an internalised norm of about 60 seconds, so a countdown would imply a deadline that does not exist. Accumulating time supplies the queue pressure instead, and the elapsed value itself (sN_time_first) is the behavioural measure. The norm is shown beside the timer as 팀 평균 ~60초. (This supersedes the August 2026 countdown and its OVERTIME flag; timer_sec and sN_expired no longer exist.)
Timing audit — two defects found and fixed. Both would have made sN_time disagree with the task as the participant experienced it, which is exactly the discrepancy flagged from a prior project. (1) The clock used to stop on the first decision click while the exported time kept advancing to the latest click, so an officer who decided at 0:10, read on, and switched at 0:40 was recorded at 40 s against a display frozen at 0:10. The clock now runs until they advance, and the two moments are exported separately as sN_time_first and sN_time_final. (2) The display counted setInterval ticks while the export read the wall clock, so the two drifted apart whenever timers were throttled — a backgrounded tab clamps and coalesces them. The display is now derived from the same wall clock as the export, leaving only sub-second floor() rounding between them. Measured after the fix: screen 13 s vs export 13,816 ms, and the gap no longer accumulates.
Officers cannot deny entry. Denial is an administrative decision taken above the frontline after secondary review, so the interface offers, left to right by severity, Allow Entry, Secondary — Checking / Requesting Further Information, and Secondary — Recommending Rejection. The three buttons are deliberately uncoloured — a green/amber/red ramp would nudge severity perception independently of the AI manipulation. Either secondary option reveals an optional free-text box (300 characters) for the basis of the referral. The old Deny Entry button is gone, and sN_dec is now coded a / sr / si / NA.
The AI panel shows a decision, not a risk score. The numeric NN/100 figure, the green-to-red risk bar and its LOW … HIGH axis have all been removed, along with the colour coding on the recommendation badge. What the officer now sees is the AI's recommended decision and its confidence in that recommendation — relabelled from the old 신뢰도 to make clear it is the system's certainty about its own output, not an independent risk metric. Scenario data still carries ai.score and ai.level, but nothing renders them. This narrows what transparent toggles: it now controls only the contributing-factors list. The confidence line has its own switch, show_confidence, so the panel can be run as recommendation + confidence + factors, any pair, or a bare recommendation with no numbers at all.
Confidence values are authored, not computed. Each scenario carries a hand-written ai.conf integer in assets/scenarios.json (range 61–97, mean 78). They were written as a companion to the numeric risk score, loosely tracking its distance from 50 — so a mid-range score got a low confidence. That score is no longer displayed, which leaves confidence as the only number the officer sees, carrying weight it was never calibrated for. The three AI-error trials sit at S5 68, S9 78, S13 68. Worth a deliberate pass before a live wave — or run show_confidence=0.
Panel attention is exported directly, not only inside events_log. Every + View and every collapse is timed, and the per-panel result is promoted into its own URL parameters (sN_panel_opens, sN_panel_dwell, sN_panel_first) so it survives the length guard — events_log is the first thing shed when the URL runs long, and on a realistic 15-case session it is shed. The trade-off is budget: these three families cost about 2,600 characters, which is what prompted raising the cap to 16,000 so referral comments are no longer squeezed out. Watch the QA line under ?debug=1, which prints the exact redirect length.
Passenger details live behind the panels. The scenario subheader shows only Passenger N of 15. Name, case ID, nationality, age/sex and purpose are no longer previewed above the fold — every piece of case information requires an explicit panel open, so sN_panels and sN_panels_open measure information seeking without anything being given away for free.
Leave order unset in production. Omitting it gives each participant a fresh shuffle with the three AI-error trials (S5, S9, S13) confined to positions 3–11 of 15 — never the first three or last three — and never two of them adjacent. order=random is the opposite — one fixed sequence for everyone — so use it for pilots and demos, not for a live wave where you want order counterbalanced across participants.

The app always exports the values it actually used, so the condition each participant ran is recoverable from the returned data alone. The sequence actually presented always comes back as scenario_order, whichever mode produced it. A queue_size outside {50, 200, 500} falls back to 200, and an unrecognised order value falls back to the default per-session shuffle.

▸ Randomizing across participants 참가자별 무작위 배정

The manipulated factor is transparency (2 cells). Queue load is a between-subjects condition that can be treated as a factor or as a covariate. Pick one of the two designs below.

A third switch exists: show_confidence. It is not part of either design below, which assume it is held constant at its default 1. Crossing all three (transparency × queue × confidence) would give 12 cells — with ~1,000 officers that is ~83 per cell, thin for detecting an interaction. Treat confidence as a held-constant design choice unless the team decides otherwise; if you do manipulate it, add a two-path randomizer and re-plan cell sizes, because neither table below accounts for it.

Approach A — Recommended

Randomize transparent and queue_size independently per participant. Transparency is the manipulated factor; queue load enters analysis as a covariate first and as a moderator in follow-up, which is the recommendation while cell sizes are uncertain.

# Transparent (AI explanation shown)
survey.html?transparent=1&queue_size=<50|200|500>&show_confidence=1&guid=<RESPONSE_ID>&return_url=<QUALTRICS_RETURN>

# Opaque (recommendation + confidence only, no explanation)
survey.html?transparent=0&queue_size=<50|200|500>&show_confidence=1&guid=<RESPONSE_ID>&return_url=<QUALTRICS_RETURN>

Approach B — Full factorial

▸ Wiring it up in Qualtrics Qualtrics 연동

Don't hand out static per-participant URLs. Qualtrics assigns the condition and builds the URL for each respondent on the fly, piping its own ResponseID in as the guid.

  1. Randomize the condition. Add an Embedded Data field transparent, then use a Randomizer that sets transparent=1 on one path and transparent=0 on the other (Evenly Present = balanced). Add a second Embedded Data field queue_size with its own randomizer over 50/200/500 (or 6 combined paths for Approach B). Add a third, show_confidence, set to a constant 1 unless you are manipulating it — in which case give it its own two-path randomizer.
  2. Place the task on a survey page as a full-width iframe or a redirect, with parameters piped from embedded data:
survey.html?transparent=${e://Field/transparent}&queue_size=${e://Field/queue_size}&show_confidence=${e://Field/show_confidence}&guid=${e://Field/ResponseID}&return_url=${e://Field/return_url}

Piping show_confidence is worthwhile even when you are not manipulating it — set the embedded-data field to a constant 1. The value then comes back in the export, so the condition each participant ran is recoverable from the data alone rather than from your memory of how the wave was configured. Drop it from the URL only if you are content to rely on the default.

  1. Set return_url to the survey's own continue URL. When the participant finishes, the task auto-returns them there with all behavioral data appended (no click needed).
  2. Capture the returned data by declaring matching embedded-data fields on the return page (see next section).

Those are the only parameters production needs. The rest — order, order_seed, auto_return, return_delay, debug — are deliberately left at their defaults in a live wave; each is described in the URL parameters table above, and debug must never be set in production.

Keep guid = ResponseID. That single key is what lets you join the rich behavioral export to each Qualtrics response afterward.

▸ Collecting the data back 데이터 수집

When the participant finishes the 15th decision, the app builds one query string of all results and redirects the browser to return_url with it appended. Two safeguards make this reliable in the field:

  • Auto-return fires on its own (default 6 s, tunable with return_delay) so data still returns if the participant walks away — a "Submitting your data…" banner and a manual button back it up. Off in debug.
  • URL-length guard. Referral comments are the volatile part: Korean percent-encodes to about nine characters each, so fifteen filled comments can still exceed the cap on their own. The cap is 16,000 characters — raised from 7,500, which had become tight enough that ordinary sessions were shedding comments once per-panel timing joined the export. 16,000 is about half of Chrome's practical ceiling, and a realistic 15-case session with Korean notes lands near 6,100. The app sheds the bulky events_log first, then the comments, setting events_log_dropped=1 and comments_dropped=1 so the loss is visible in the data. All summary fields always survive, and the complete record stays recoverable via Copy export data.

To record the data, point return_url at a Qualtrics survey and add an Embedded Data element at the top of its Survey Flow listing every field name below (no values) — Qualtrics auto-fills each from the matching URL parameter. Because guid = ResponseID, join on guid to attach it to the participant's response.

The Embedded Data field list changed shape — not just size. Six families were removed (timer_sec, sN_expired, n_expired, sN_correct, sN_difficulty, sN_override) and new ones added (queue_size, show_confidence, sN_comment, sN_panels_open, sN_panel_opens, sN_panel_dwell, sN_panel_first, fp2_caught), while n_correct was renamed correct_total. Delete the retired fields and add the new ones before your next wave, or you will collect empty columns alongside stale ones.

Field(s)Contents
guidSession ID = the Qualtrics ResponseID you passed in. Join key.
queue_size, transparent, show_confidenceThe between-subjects conditions this participant actually ran. show_confidence is new: 1 when the AI's confidence line was displayed.
scenario_orderThe 15 scenario ids in the order actually presented.
order_mode, order_seedHow that order was produced (shuffle/random/default/explicit); the seed appears only in random mode.
sN_decDecision on scenario N: a = Allow, sr = Secondary recommending rejection, si = Secondary requesting information, NA = no decision.
sN_time_firstReplaces sN_time. Elapsed ms from the passenger appearing to the first decision click. This is the time-pressure DV — it is the moment of commitment, uncontaminated by any later reconsideration.
sN_time_finalNew. Elapsed ms to the last decision click. Equal to sN_time_first unless the officer changed their mind; the gap between them is time spent reconsidering.
sN_dec_changesNew. How many times the decision was switched to a different option after the first click. 0 for the overwhelming majority; above 0 means sN_dec is a revised answer, and the two time fields will differ.
sN_panelsDistinct case-file panels opened on scenario N (0–4) — per-trial depth of review.
sN_panels_openNew. Which panels were opened on scenario N, as a comma list in fixed order (profile,doc,db,apis) — empty when none were. Emitted as one field per scenario rather than four 1/0 columns to keep the return URL clear of the length cap; split into dummies in analysis. Open order and timings remain in events_log.
sN_panel_opensNew. How many times each section was expanded on scenario N, as panel:count (e.g. profile:2,doc:1). A count above 1 is a revisit — the officer went back to a section after closing it. Panels never opened are omitted.
sN_panel_dwellNew. Total milliseconds each section spent expanded, as panel:ms. Summed across revisits, and a section still open when the officer advances is closed out at that moment. Panels can be open simultaneously, so these need not sum to sN_time_final.
sN_panel_firstNew. Milliseconds from the passenger appearing to the first expansion of each section, as panel:ms. Sorting these gives the order sections were consulted in.
sN_commentNew. Free-text basis for a referral, up to 300 characters. Empty for Allow decisions and whenever the officer left it blank.
correct_total, panels_totalSession rollups across all 15 trials. correct_total was previously named n_correct.
fp_caught, fn_caught, fp2_caughtThe three AI-error trials: 1 when the officer overrode the AI correctly — S5 Allowed, S9 sent to secondary recommending rejection, S13 Allowed. fp2_caught is new.
events_logJSON blob with the raw open sequence plus every comment. Expect it to be absent. It duplicates the whole export and costs ~14,000 characters encoded, so it is shed on any full session — keeping it would need a ~20,000-char cap. Everything analytically useful in it is now promoted to its own column, so its loss costs you only the exact open sequence, which sN_panel_first already orders.
events_log_dropped, comments_dropped1 only when the URL guard had to shed that part to stay under the length cap; absent otherwise. See below.
Single-response alternative. If you need the task data on the same Qualtrics row rather than a joined one, embed survey.html in an iframe inside a question and post the results to the parent with window.postMessage, then write them to embedded data with question JavaScript. That's more setup than the join-by-guid flow above, and only worth it if a second linked record is a problem for you.
