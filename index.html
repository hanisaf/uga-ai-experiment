AI-Assisted Passenger Screening · AI 보조 출입국 심사

Design overview and test URLs for the behavioral screening task. Participants review 12 fictional passenger case files alongside a simulated AI risk score under a countdown timer, and decide Allow / Secondary / Deny for each. Behavioral data is exported back to Qualtrics via URL parameters.

Behavioral task · 12 scenarios   |   Safadi · Kim · Schanke — UGA / UCF · July 2026

▸ Launch the task 과제 실행

The instrument is the single file survey.html. It loads assets/scenarios.json and the images in assets/ at runtime, so it must be served over HTTP — opening it as a file:// path will hang on "Loading case files…". Every link on this page is relative, so it works on any host.

Serving locally

From inside the design_handoff_screening_terminal/ folder:

python3 -m http.server 8731
# then open  http://localhost:8731/

Any static server works (npx serve, php -S, nginx, S3…). The only requirement is that index.html, survey.html, and assets/ are served from the same origin.

Production hosting

Upload survey.html, this index.html, and the entire assets/ folder (same relative paths) to any static host. The participant-facing URL is then https://YOUR-HOST/path/survey.html?….

▸ URL parameters URL 매개변수

All parameters are read from the query string (?key=value&key=value).

ParamValuesDefaultRole in the study
transparent 1 / 0 1 Between-subjects IV. 1 shows the AI's bilingual "Contributing factors" list; 0 hides it (score + recommendation only). This is the condition you randomize.
timer_sec int 5–600 random U(30,90) Continuous covariate. Countdown seconds per passenger. On expiry the trial is flagged OVERTIME — nothing is auto-decided and nothing is skipped. Leave unset in production so the app draws a fresh random value per participant; set it only for piloting/QA or a bucketed factorial design.
order random / default / id list per-session shuffle Presentation order. Omit for the production design (fresh constrained shuffle per participant). random = the same constrained shuffle for everyone, from order_seed; default = authored order; a comma-separated id list forces that exact sequence (omitted ids are appended, never dropped).
order_seed int 42 Seed for order=random. Ignored in every other mode.
guid string auto UUID Session ID written into the exported data. Pass the Qualtrics ResponseID here so behavioral records join back to the survey response.
return_url URL none Qualtrics survey URL to redirect back to on completion; the export query string is appended. Required to collect data back.
auto_return 1 / 0 on in prod Auto-redirect to return_url when the session ends, so data isn't lost if the participant closes the tab. On whenever return_url is set; off in debug.
return_delay int 0–60 6 Seconds the results screen shows before auto-return. 0 = redirect immediately.
debug 1 / 0 0 QA only — shows each scenario's difficulty rating inline and disables auto-return so you can inspect the export screen. Never enable in production.
Careful with transparent. The default 1 applies only when the parameter is absent. Any other present value (e.g. 2, yes, empty) is treated as 0 (opaque) — so always pass exactly 1 or 0.
When the timer runs out. The countdown is a time-pressure manipulation, not a deadline. On expiry the pill reads OVERTIME · 제한시간 초과, the bar goes full-width dark red, and an inline bilingual notice asks the participant to record a decision — but nothing is decided for them and the task does not advance. All three buttons stay live. The trial is flagged sN_expired=1, so an overtime trial still yields the participant's own decision and can be scored correct. (Earlier builds auto-recorded "Secondary" and skipped ahead.)
Leave order unset in production. Omitting it gives each participant a fresh shuffle with the AI-error trials (S5, S9) kept out of the first two and last two positions. order=random is the opposite — one fixed sequence for everyone — so use it for pilots and demos, not for a live wave where you want order counterbalanced across participants.

The app always exports the values it actually used, so a self-randomized timer is still recorded per participant — you don't need to pass it in to capture it. The same applies to ordering: the sequence actually presented always comes back as scenario_order, whichever mode produced it. timer_sec outside 5–600 is ignored and the app randomizes instead; an unrecognised order value falls back to the default per-session shuffle.

▸ Randomizing across participants 참가자별 무작위 배정

The manipulated factor is transparency (2 cells). Time pressure is a continuous covariate. Pick one of the two designs below.

Approach A — Recommended

Randomize transparent per participant; let the app self-randomize the timer. Transparency is the manipulated factor; time pressure stays a true continuous covariate captured on the way out.

# Opaque (score only, no explanation)
survey.html?transparent=0&guid=<RESPONSE_ID>&return_url=<QUALTRICS_RETURN>

▸ Wiring it up in Qualtrics Qualtrics 연동

Don't hand out static per-participant URLs. Qualtrics assigns the condition and builds the URL for each respondent on the fly, piping its own ResponseID in as the guid.

  1. Randomize the condition. Add an Embedded Data field transparent, then use a Randomizer that sets transparent=1 on one path and transparent=0 on the other (Evenly Present = balanced). For Approach B, use 6 paths that set both transparent and timer_sec.
  2. Place the task on a survey page as a full-width iframe or a redirect, with parameters piped from embedded data:
survey.html?transparent=${e://Field/transparent}&guid=${e://Field/ResponseID}&return_url=${e://Field/return_url}
# Approach B: also append  &timer_sec=${e://Field/timer_sec}
  1. Set return_url to the survey's own continue URL. When the participant finishes, the task auto-returns them there with all behavioral data appended (no click needed).
  2. Capture the returned data by declaring matching embedded-data fields on the return page (see next section).
Keep guid = ResponseID. That single key is what lets you join the rich behavioral export to each Qualtrics response afterward.

▸ Collecting the data back 데이터 수집

When the participant finishes the 12th decision, the app builds one query string of all results and redirects the browser to return_url with it appended. Two safeguards make this reliable in the field:

  • Auto-return fires on its own (default 6 s, tunable with return_delay) so data still returns if the participant walks away — a "Submitting your data…" banner and a manual button back it up. Off in debug.
  • URL-length guard. A full record (~4.5 KB) sits well under the ~8 KB Qualtrics accepts. If the URL ever exceeds 7500 chars, only events_log is dropped (summary fields still sent) and events_log_dropped=1 is flagged; the full trace stays recoverable via Copy export data.

To record the data, point return_url at a Qualtrics survey and add an Embedded Data element at the top of its Survey Flow listing every field name below (no values) — Qualtrics auto-fills each from the matching URL parameter. Because guid = ResponseID, join on guid to attach it to the participant's response.

The field list grew from 59 to 85. order_mode, order_seed, and a sN_expired + sN_panels pair for all 12 scenarios are new. Add them to the Embedded Data element before your next collection wave, or those columns arrive empty.
